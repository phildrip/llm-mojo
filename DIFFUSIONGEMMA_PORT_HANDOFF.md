## What's done (committed through `cacbdf0` + uncommitted Opt A, working)

The full DiffusionGemma inference path runs end-to-end. Verified output:
`"hello"` → `"<channel|>Hello! How can I help you today?<eos>..."`
in ~4-12 denoise steps (seed dependent), ~120-240s total.

**Opt A (SIMD attention) is implemented and committed in the working tree.**
The attention inner loops in `attn_worker` now use `SIMD[DType.float32, 8]`
loads + multiply + `reduce_add` for the score loop, and loop-swapped
SIMD8 accumulate for the value-sum loop (zero → accumulate → store).
This follows the exact pattern from `model.mojo:2314-2338` (a proven
SIMD16 attention for the same model). Attention dropped from ~230ms/layer
to ~20ms/layer (~11× speedup). Total step time: 28s → ~23.5s.

**`q4_gemv_batch`** (the key optimization, lines ~430-495): takes
`B × c_in` X matrix with `in_stride`/`out_stride` params (for aligned buffers
like `canvas_q` which uses `MAX_Q_SIZE=8192` stride even on sliding layers with
`q_size=4096`). Loads each weight block ONCE, loops over all B in the inner.
Parallelizes across `c_out` rows via `parallelize[worker](tasks)`. Default
stride params (-1) fall back to `c_in`/`c_out` for tight buffers.

**`main()` layout** (approximate line numbers):
- 620-700: Load `diffusiongemma_q4.bin` (14.3GB) via posix_memalign + chunked read.
- 700-755: Load final_norm, SC, embeddings.
- 755-870: KV cache allocation (`max_seq_len × Σ layer kv_stride`).
- 870-940: Activation buffers + canvas buffers + sampler buffers.
  Canvas hidden `[256, 2816]`, canvas_q `[256, 8192]` (MAX_Q_SIZE aligned),
  canvas_k/v `[256, 4096]` (MAX_KV_SIZE), canvas_attn_out, canvas_proj_attn,
  canvas_norm, canvas_ffn_* (5 intermediates), canvas_moe_*, canvas_combined.
  Per-token scratch: `canvas_attn_scores [256, 512]`, `canvas_exp_*`
  `[256, top_k × {2*704, 704, 2816}]`, `canvas_router_scores`, `canvas_top_*`.
- 940-960: Tokenizer (Python FFI).
- 960-end: Per-turn chat loop:
  - Prefill (token-first, causal): `for pos in range(num_prompt_tokens)`,
    same as old AR path. Writes K/V for prompt positions. Still uses the
    original per-token `q4_gemv_cpu` (not batched) since prefill typically
    short (~10-100 tokens, not worth batching).
  - Canvas init: `np.random.randint(0, vocab_size, 256)`, zero `sc_embeds`.
  - Denoise loop: see below.

**Denoise step structure** (the hot path, ~28s/step):

1. **Canvas embed + SC** (per-token, ~2s): for each of 256 canvas tokens,
   `embed.reconstruct(token)` → scale by `sqrt(2816)` → `sc_forward(...,
   sc_embeds, ...)` writing back into `canvas_hidden`. SC soft_embeds is zero
   on first step (no previous probs).

2. **Decoder forward** (layer-first, ~22s total for 30 layers, ~750ms/layer):
   For each of 30 layers:
   - Phase 1a (batched, ~130ms): `rms_norm_batch` on canvas_hidden →
     `q4_gemv_batch` for wq, wk, wv (either separate or `v = k` for global).
   - Phase 1b (per-token, ~30ms): head norms (q_norm, k_norm, v_norm) +
     `apply_rope` with `pos = num_prompt_tokens + t` + write K/V into cache
     at canvas slot positions. K/V slots are reused each denoise iteration
     (matches vLLM — `num_computed_tokens -= num_rejected` semantics).
   - Phase 2a (parallelized over 256 tokens, ~230ms): bidirectional attention
     with `seq_len = num_prompt_tokens + CANVAS_LEN`. Each worker handles one
     canvas token: 16 heads × `seq_len` dot products × softmax × value sum.
     Writes into per-token `canvas_attn_out`. **Still scalar inner loop** —
     the `for d in range(layer_head_dim)` for score and value sum does not
     use SIMD. This is the single biggest remaining opportunity.
   - Phase 2b (batched, ~25ms): `q4_gemv_batch` Wo projection,
     `rms_norm_batch`, residual add into canvas_hidden.
   - Phase 2c (batched, ~100ms): shared MLP path - gate/up/down via
     `q4_gemv_batch`, `gelu_and_mul_batch`, `rms_norm_batch`.
   - Phase 2d (parallelized over 256 tokens, ~300ms): MoE path. Each worker
     does one canvas token: router q4_gemv, softmax, top-k, per-expert
     (sequential, 8 experts) gate_up + gelu_and_mul + down q4_gemvs, weighted
     sum. `top_idx`/`top_weights`/`moe_in`/scratch are all per-token (no races).
     Experts are NOT batched across tokens that pick the same expert — each
     token's 8 expert matmuls read its own copy of expert weights.
   - Phase 2e (per-token, ~70ms): combine shared + MoE, final norm,
     residual, multiply by layer_scalar.

3. **Sampler** (~3.4s):
   - Batched logit projection: `q4_gemv_batch` with `B=256, c_in=2816,
     c_out=262144` reads 370MB embed weights ONCE. Writes `[256, 262K]`
     `canvas_logits`. Note: `q4_gemv_batch` produces raw dot products;
     `tanh(x/30)*30` softcap is applied in the per-token worker below
     (NOT inside `q4_gemv_batch` — this is intentional; the batched matmul
     is generic).
   - Parallelized per-token worker (256 workers, each single-threaded):
     scale logits by `1/temp`, softcap, log-softmax (manual max + exp + sum
     + log), entropy (`-sum p * log(p)`), argmax, categorical sample
     (cumsum vs uniform random), `probs_to_soft_embed` (uses
     `num_tasks=1` to avoid nested parallelize).
   - Entropy-bound mask: selection sort 256 positions by ascending entropy,
     cumsum + cummax, accept positions where `(cumsum - cummax) ≤ 0.1`.
   - Canvas update: accept → sampled token, reject → random re-noise
     (batched `np_random.randint`).
   - History: 2-slot circular buffer of argmax canvases. Stable if equal.
   - Convergence: `(stable AND confident AND hist_len ≥ 2) OR (step+1 ≥ 48)`.
     On convergence: snap canvas to argmax, break.

### `q4_embed.mojo` (277 lines)

`Q4Embedding` struct with:
- `reconstruct(token, out_ptr)` — load 1 row from q4 packed weights, write
  2816 floats. Used by canvas embed and AR prefill.
- `project_logits_parallel(x, max_logits, next_tokens, num_tasks)` — old AR
  path, parallelized over vocab with per-task argmax. Computes
  `tanh(x*W/30)*30` inline. Still used by prefill.
- `project_full_logits(x, out_logits, num_tasks)` — new for sampler. Writes
  full `[262K]` logit vector (with softcap). `num_tasks=1` skips
  `parallelize` to avoid thread sync overhead when called inside an outer
  `parallelize[sampler_worker]`. Used by the original per-token sampler
  path (now superseded by `q4_gemv_batch` in the batched path, but kept for
  correctness comparisons).
- `unpack_16bytes` — the q4 unpack helper (duplicated between files for
  inlining; Mojo doesn't have cross-file `@always_inline` reliably).

## Performance: where the time goes (~23.5s/step, post-Opt-A)

Per-layer breakdown from profiling (averaged over layers 0, 15, 29):

| Phase | ms/layer | × 30 | Notes |
|---|---|---|---|
| QKV proj (batched) | 130 | 3.9s | `q4_gemv_batch` with B=256; weights read once. Good. |
| Head norms + RoPE + cache write | ~30 | 0.9s | Per-token, scalar. Cheap. |
| Bidirectional attention | ~20 | 0.6s | **SIMD-ized (Opt A done).** Was 230ms/layer, now ~20ms. |
| Wo proj (batched) | ~25 | 0.75s | Good. |
| Shared MLP (batched, 3 matmuls) | 100 | 3.0s | `q4_gemv_batch` good but B-loop is sequential inside worker — no L1 tiling. |
| MoE router | ~5 | 0.15s | Per-token, num_tasks=1. Cheap. |
| MoE experts (8 per token × 256) | 300 | 9.0s | Parallelized over 256 tokens but each token's 8 expert matmuls hit random expert weights. **L3 thrash. Now the #1 bottleneck (38% of step time).** |
| Final combine + norm | ~70 | 2.1s | Per-token scalar. |
| Sampler logit proj (batched) | ~1100 | once | 370MB embed weights read once. Good. |
| Sampler softmax+entropy+sample+sc | ~2400 | once | Parallelized over 256 tokens, single-threaded inner. Softmax loop is the bulk (`for v in range(262K)` ×2). |
| **Total/step** | | **~23.5s** | Down from ~28s (Opt A saved ~4.5s). |

**L3 budget**: 64MB L3 total, ~32MB usable per worker (8 cores). Weights per
layer ~20MB packed. Single-layer weights fit, but the per-token MoE access
pattern across 8 experts jumps through ~80MB of expert weight space per
token, blowing L3 every token. The batched matmul's 256-wide X matrix
(256 × 2816 × 4B = 2.8MB) fits in L2 but the per-row weight block load (16B)
is tiny — most of the time is weight streaming from DRAM.

### Hardware budget reminder

- AMD Ryzen 7 5700G APU, 8 cores / 16 threads, 64GB DDR4-3200, ~57 GB/s
  shared bandwidth (40 GB/s realistic under contention).
- 32MB L3 (8-core shared), 512KB L2 per core, 32KB L1 data per core.
- Vega 8 iGPU (gfx90c) available via direct `/dev/kfd` (`test_kernels.mojo`
  has a working KFD FFI binding — not required for current CPU path).
- AR decode was ~4.5 tok/s on the original `model_speculative_moe.mojo`.
  Current diffusion at 23.5s/step × 5 steps avg = 118s for 256 tokens =
  ~2.2 tok/s effective. **Still slower than AR** because the MoE expert
  weights (460MB) far exceed L3 (32MB), causing L3 thrashing in the MoE
  phase (9s/step, 38% of total). The bandwidth amplification from canvas
  diffusion (read each decoder weight once for 256 tokens) works well for
  QKV, FFN, and attention, but not for MoE where the 128-expert weight
  space is too large for any cache level.

## Remaining work (ordered by expected impact)

### Opt A: SIMD attention inner loop — DONE ✓

Implemented in the working tree (uncommitted). The `attn_worker`'s score
and value-sum loops now use `SIMD[DType.float32, 8]` loads + multiply +
`reduce_add`, following the pattern from `model.mojo:2314-2338`. Attention
dropped from ~230ms/layer to ~20ms/layer. See diff in `model_diffusion.mojo`
around line 1355.

### Opt B: Tile `q4_gemv_batch`'s inner B-loop — TRIED, DIDN'T HELP

Attempted: added a `tile_b` parameter to `q4_gemv_batch` that wraps the
`for b in range(B)` loop with `for b_outer in range(0, B, tile)` +
`for b in range(b_count)`. Tested with TILE_B=32 and TILE_B=128.

**Result:** Slightly *worse* than the original (QKV ~130ms → ~140ms/layer).
The L3 cache (32MB shared) was already handling the 2.8MB X matrix
adequately. The tiling overhead (weight block reloads per tile, runtime
`b_count` loop bounds preventing optimization, split output stores)
negated any L2 benefit. **Reverted.**

The real bottleneck in `q4_gemv_batch` is the `reduce_add` in the inner
B-loop: `(w0 * X.load[8](x_base)).reduce_add()` does a horizontal SIMD
reduction per b per block. For B=256 and 88 blocks, that's 256×4×88 =
90112 reduce_adds per row. `q4_gemv_cpu` (single-vector) does only 1
reduce_add per row (accumulates in SIMD form, reduces once at the end).
But `q4_gemv_cpu` reads the weight once per token (no B reuse), so it's
worse for large B. A custom kernel that combines SIMD accumulation
(like `q4_gemv_cpu`) with B-reuse (like `q4_gemv_batch`) would be needed
— essentially keeping B SIMD accumulators and updating them per block.
With B=256 that's too many registers, but with tiling (TILE_B=8, using
8 SIMD8 registers) it might work. This is a future optimization.

### Opt C: Batch MoE experts — TRIED, BLOCKED BY RUNTIME CRASH

Attempted: restructured MoE into (1) parallelized router pass, (2) sequential
build of expert-to-token lists, (3) per-expert batched matmuls.

**Two issues found:**

1. **`q4_gemv_batch` with small B (~16) is no faster than per-token
   `q4_gemv_cpu`.** The reduce_add overhead in the B-loop dominates at
   small B. `q4_gemv_batch` does B×4×blocks reduce_adds per row;
   `q4_gemv_cpu` does 1 per row. For B=16, the weight reuse (reading
   expert weights once for 16 tokens) doesn't compensate. MoE stayed
   at ~320ms/layer (same as the original per-token approach).

2. **Closures defined inside a `for e in range(128)` loop crash the
   Mojo runtime.** Defining `def expert_token_worker(i: Int) capturing`
   inside the expert loop and calling it (even sequentially, not via
   `parallelize`) causes a segfault in `libKGENCompilerRTShared.so`.
   This is distinct from the known-working pattern of closures inside
   the `for l in range(30)` layer loop (which `moe_worker` uses
   successfully). The difference might be the number of closure
   definitions (30 vs 3840) or the depth of loop nesting.

   **Workaround for future attempts:** inline the worker code directly
   in the loop body (no closure) for sequential execution, or define
   the closure at the `for l` level and use a flat index to encode
   (expert, token) pairs. The latter requires per-token output buffers
   and a sequential reduction to avoid races on `canvas_moe_out`.

**Reverted to original per-token `moe_worker`.** The MoE phase remains
at ~300ms/layer (9s/step, 38% of step time) — the single biggest
remaining bottleneck.

**Path forward for MoE optimization:** Write a custom `q4_gemv_small_b`
kernel that processes B~16 tokens with SIMD accumulation (not
reduce_add per b). Keep B SIMD8 accumulators in registers, load weight
block once, multiply with B X vectors, accumulate. Reduce all B
accumulators to scalars at the end. This avoids both the reduce_add
overhead and the weight re-read. Then use this kernel in the batched
expert loop (sequential experts, L3 weight reuse across tokens).

### Opt D: Multi-turn conversation (functional gap, not perf)

Currently each user turn re-runs prefill over the prompt only. vLLM does
KV-cache prefill over prompt + previously committed canvas blocks (so the
model "remembers" prior turns). To match:
- After each canvas commit, run encoder prefill over the committed
  `argmax_canvas` (256 tokens) at positions
  `[num_prompt_tokens, num_prompt_tokens + 256)`. Writes K/V permanently.
- Track a per-request `total_committed_len` that advances by 256 each turn.
- Next turn's prefill starts at `total_committed_len`; new canvas at
  `[total_committed_len, total_committed_len + 256)`.
- `max_seq_len = 512` currently supports ~1 turn. Bump to e.g. 4096 for
  multi-turn. KV cache scales linearly (currently 220MB at 512 → 1.76GB at
  4096, fine).

### Opt E: Streaming output (UX)

Currently the full 256-token canvas is decoded and printed only after
convergence. vLLM emits `argmax_canvas` at the commit step. Could stream
partial canvas during denoising (print every step's argmax to show
diffusion progress) — pure UX, no perf impact. Helpful for debugging
convergence behavior.

### Opt F: Torchaudio-level perf investigation (deferred)

The 28s/step is ~10× slower than the 2-3s/step that the handoff v1
estimated. The gap is mostly (A) and (C) above. Once those land, profile
again — the next bottleneck is likely the FFN batched matmul's
weight-streaming bandwidth (20MB/layer × 30 layers × 2 matmuls = 1.2GB
per step, at 40 GB/s = 30ms — so theoretical floor is ~3s/step). The
batched matmul may need explicit prefetch (`std.sys.intrinsics.prefetch`)
ahead of the inner block to hide DRAM latency.

### Opt G: GPU path (deferred indefinitely)

Vega 8 iGPU has ~48 GB/s and 4096 stream processors. The KFD FFI binding
in `test_kernels.mojo:1056-1889` works. Could dispatch the batched q4
matmuls to GPU and keep everything else on CPU. Not worth pursuing until
CPU path is at theoretical floor (Opt A-C done).

## Gotchas already learned (don't relearn these)

- **`out` is a reserved keyword in Mojo** — cannot be a parameter name or
  local var. Use `sc_out`, `out_ptr`, etc.
- **Default parameter values are immutable** — `in_stride: Int = -1` then
  `if in_stride < 0: in_stride = c_in` fails with "invalid redefinition".
  Use `var x_stride = in_stride if in_stride >= 0 else c_in`.
- **Nested `parallelize` is broken** in current Mojo — oversubscribes the
  shared pool. Keep all `parallelize` calls single-level. The MoE worker
  does its 8 expert matmuls **sequentially** (1 thread) inside an outer
  `parallelize[moe_worker](256)`. Handoff v1 said "8 parallel experts, 1
  thread each, 1 outer parallelize" was correct — that was for AR which
  has 1 token; for diffusion we have 256 tokens so the outer 256 is the
  right parallelism.
- **`MutExternalOrigin` deprecated in 1.0.0b2** — warnings only, use
  `MutUntrackedOrigin` for new code (existing code still compiles with
  warnings; we left existing to avoid churn).
- **`out` parameter convention is reserved** too (out parameter for
  constructors). Don't name anything `out`.
- **Closure captures in `parallelize`**: `def fn(i: Int) capturing -> None`
  is fine. Closures defined inside the **per-layer** loop (30 iterations)
  work correctly (`moe_worker`, `attn_worker`, etc.). **BUT: closures
  defined inside a `for e in range(128)` loop (3840 total iterations) crash
  the Mojo runtime** (`libKGENCompilerRTShared.so` segfault). This was
  discovered during Opt C. Inline the worker code directly in the loop
  body for sequential execution, or define the closure at the `for l`
  level and encode sub-indices in the task index.
- **Python FFI**: `np_random.rand(N)` returns a PythonObject; index with
  `[t]` and wrap with `Float32(Float64(py=...))` to materialize. For
  `np_random.randint(low, high, N)`, same pattern.
- **`len(s)` on String is deprecated** — use `s.byte_length()` or
  `s.count_codepoints()`. Existing code still compiles with warning.
- **`mojo build` fails** with `ld.bfd: DSO missing from command line` for
  libm.so.6. **`mojo run` works** (JIT, no separate link step). Don't waste
  time on the build error.
